## Standard planning-to-execution workflow

RAHSA now uses this standard workflow:

```text
Discussion / research in ChatGPT
→ PRD
→ TSD / ADR / Threat Model as needed
→ phase TASKS drafted
→ owner approval
→ ChatGPT prepares JIT Implementation Kit for next Txxx
→ TASKS activates exactly one Txxx + ACTIVE_KIT
→ Codex preflight
→ Codex executes/reviews/builds/tests exactly one task
→ focused checkpoint
→ TASKS returns to PLANNING_FREEZE / NONE / NONE
→ return to ChatGPT/owner before next task
```

Implementation Kit rules are defined in `docs/IMPLEMENTATION_KIT.md`.

The required task kit manifest is:

```text
implementation-kits/Txxx/README.md
```

Patch and PowerShell helpers are optional. They exist to reduce repeated exploration/mechanical work, not to replace Codex review or higher-level governance.

Kits are prepared just-in-time for the next task against the latest verified checkpoint. Full phase patches are not pre-generated by default because earlier task commits can stale later patches.

## Reuse-first rule

For new capability design and implementation, evaluate in order:

1. Retained RAHSA implementation.
2. Upstream KeyPass implementation/pattern.
3. Android/AndroidX/Jetpack.
4. Mature, maintained, license-compatible OSS.
5. Minimum local implementation.

Security-sensitive reuse requires review. New dependencies require purpose/source/license/justification/security-impact documentation.

Verified reuse findings should be carried into the next task's Implementation Kit to reduce repeated repository exploration, while security-critical assumptions remain subject to re-check.

## Implementation Kit and Codex gate

Codex may modify application code only when `TASKS.md` exposes exactly one approved active Txxx and one repository-local active kit, and repository preflight passes.

Codex must run:

```powershell
python scripts/governance_preflight.py --implementation Txxx
```

Preflight checks task status, task identity, active kit path, kit task identity, and `KIT_STATUS: READY`.

If no task/kit is active, Codex must stop without application-code changes.

After a successful task checkpoint, Codex must return the execution gate to:

```text
EXECUTION_STATUS: PLANNING_FREEZE
ACTIVE_TASK: NONE
ACTIVE_KIT: NONE
```

Codex does not automatically continue to the next task.

## Cost policy

Use the lowest-cost model/reasoning that is reasonably sufficient.

Classify inherent risk first, then use kit completeness to reduce exploration cost where safe:

- deterministic low-risk kit / inspection / mechanical / smoke work → Luna + low;
- low-risk kit needing limited adaptation → Luna + low/medium;
- normal focused implementation/review → Terra + medium;
- security-sensitive vault/master-password/authentication/Keystore/recovery semantics, architecture-critical complexity, difficult concurrency/lifecycle problems, or failed cheaper attempts → consider Sol with justified reasoning.

A prepared patch does not lower the security-risk classification of a task. Do not default to the highest model or reasoning level, and do not sacrifice independent security verification merely to save tokens.
